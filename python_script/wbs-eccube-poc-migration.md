## Epic: EC-CUBE Migration POC

**Epic Description:**
> Prove, end to end on local and dev environments only, that MrMax can leave EC-CUBE 4.1.2 by first extracting all 89 core customisations and the GMO-PG plugin into supported extension points (Phase 1), then swapping the core to 4.2.3-p2 on PHP 8.1 (Phase 2) and moving to the 4.3 stack on MySQL 8.4 (Phase 3), closing with a measured POC report and recommendation for the real migration.

### Story 1: Phase 1 — Baseline Analysis & Sanitised Reference Database

**Type:** Story | **Priority:** H | **Points:** 3 | **Sprint:** 1

#### Story Overview
This story establishes the measurable starting point for the whole MrMax staged-migration POC before a single line of code is changed. It compares the MrMax tree against a clean EC-CUBE 4.1.2 release and records all 89 patched core files, which become the work list for the Phase 1 extraction and the reference for the Gate A core-integrity check. It also produces the sanitised local reference database: a dump of the running local project with every personal field replaced by same-shape fake values, frozen and restored fresh for every later run. No production or live data is used at any point in the programme. Missing data conditions that later test cases depend on (saved cards, soft-deleted rows, multi-class products, historical orders) are generated by a traceable seed script. Finally, today's test results, coverage, runtime versions, cron jobs and installed plugins are recorded as the "before" state. The audience is the POC delivery team (developers, QA, DevOps) and the client stakeholders who will read the final POC report. Every later story in all three phases measures against the artefacts produced here, so the story blocks everything downstream.

- **Linked Requirements:** P1-01, P1-02, P1-03, P1-04
- **Affected Components:** src/Eccube/ (read-only diff source), app/Plugin/ (inventory), composer.json / composer.lock, package.json, docker-compose.yml / docker-compose.mysql.yml (local DB), crontab / batch definitions (buildspec-batch.yml, Dockerfile-batch), phpunit.xml, POC artefact folder (e.g. docs/poc/baseline/)
- **Scope:** Backend (analysis, database, tooling)
- **Associated Epic:** EC-CUBE Migration POC

### Story 3: Phase 1 — Extract Core Customisations into app/Customize

**Type:** Story | **Priority:** H | **Points:** 13 | **Sprint:** 2

#### Story Overview
This story removes MrMax's customisations from the EC-CUBE core so that src/Eccube becomes byte-identical to the pinned 4.1.2 release, which is the prerequisite for every later wholesale core swap (4.2, then 4.3). Using the changed-file list from P1-01, it moves 25 customised entity files, 10 repository files, 25 listeners/services/controllers/form types, 22 page templates and 7 master data and translation files into EC-CUBE's supported extension points: entity traits and extensions, repository wrapping/decoration, event subscribers, service decoration, form extensions and the app/template override locations. One migration re-applies the 13 NOT NULL to NULL relaxations and keeps the birthday column a plain date, with each relaxation documented and handed to the schema drift gate as its allowlist. The 4 custom columns and all custom query method signatures stay intact, and the container must still compile in dev, prod and test. A QA reconciliation confirms no column, index, constraint or row was lost and that soft delete still filters correctly; any difference blocks the step. Developers benefit from a clean, upgradeable core, and the business keeps identical shop behaviour. The work depends on the green suite and behaviour baseline from Story 2 and feeds the CI gates in Story 4.

- **Linked Requirements:** P1-09, P1-10, P1-11, P1-12, P1-13, P1-16
- **Affected Components:** src/Eccube/ (restored to pristine 4.1.2), app/Customize/Entity (traits, e.g. CustomerTrait/OrderTrait/CartItemTrait), app/Customize/Repository, app/Customize/EventListener, app/Customize/Service, app/Customize/Controller, app/Customize/Form (extensions), app/config/eccube/services.yaml (Customize registrations), app/template/default, app/template/admin, app/Customize/Resource/locale (messages.ja.yaml / validators.ja.yaml), app/DoctrineMigrations (one POC migration)
- **Scope:** Full-stack (backend, templates, database)
- **Associated Epic:** EC-CUBE Migration POC

#### Sub-task List
- [ ] 3.1 — [P1-09] Move 25 customized entity files out of the core, keeping the 4 custom columns (Backend, 16h)

### Story 4: Phase 1 — CI Integrity Gates (Core Diff & Schema Drift)

**Type:** Story | **Priority:** H | **Points:** 3 | **Sprint:** 2

#### Story Overview
This story locks in the result of the Phase 1 extraction with two automated CI gates that run on every branch. Gate A compares src/Eccube byte for byte against the pinned official EC-CUBE release and fails the build on any difference, which is what stops the core being patched again under deadline pressure and keeps later core upgrades as wholesale swaps rather than merges. Gate B compares the live schema against an allowlist and fails the build if a column would be dropped or silently changed. The Gate B allowlist is generated from the step 3 divergence list produced by P1-10, never maintained by hand, so the ledger and the gate can never become two separately maintained lists. Developers and reviewers get immediate, objective feedback on every push. Both gates are reused, with the pinned release updated, in Phases 2 and 3. ### Story 9: Phase 2 — PHP 8 Code Compatibility & Static-Analysis Tooling

**Type:** Story | **Priority:** H | **Points:** 5 | **Sprint:** 5
